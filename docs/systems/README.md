# 系统文档

每个需要的系统建立一份 Markdown 文档，设计在前，实现说明在后。复杂实现再拆附属文件并链接，不强制策划与技术分文件。

复制下方骨架为实际系统名，删除不适用的提示，不填写虚构完成结果：

```markdown
# 系统名称

## 体验目标
玩家应感受到或能够完成什么；为什么需要这个系统。

## 玩法与规则
操作、流程、反馈、数值规则、失败恢复及与其他系统的关系。

## 设计状态与边界
| 事项 | 确认状态 | 来源与认可范围 | 可调整部分 |
| --- | --- | --- | --- |

## 当前落实情况
| 设计事项 | 实现状态 | 已验证范围/缺口 | 验收入口 |
| --- | --- | --- | --- |

## 实现说明（AI 维护）
关键代码入口、配置、依赖、非显而易见的限制和修改注意事项。
```

设计状态遵循 AGENTS.md；实现状态可以是未实现、部分实现、已实现待验收、已验收指定范围。两者独立，不能根据运行成功推定设计确认。

对用户已确认规则做重大改变前先对齐；在授权范围内可以完善暂定设计。必要时标注变更原因，历史试验过程归 Plan/验收，不持续堆在这里。代码与设计不一致时分别说明期望与现状，不为了匹配代码悄悄改设计。
