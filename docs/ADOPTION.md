# 接入与升级

接入是为了让 AI 找到用户的要求和当前设计，同时保留项目已有的有效内容和授权边界。只接入文档时，不做游戏、不提交、不推送。

## 新项目

目标目录不存在或为空时，先用 `node <框架目录>/tools/adopt.mjs --target <目标目录>` 预览，再加 `--apply` 生成骨架。工具不装引擎，不建游戏工程或 Git 仓库。

生成后填写：

- **README**：项目简介和完整的文档入口，只链接已有的资料；还没有工程时写明没有运行入口。
- **PROJECT**：用户确认过的目标玩家、体验、循环、要求和排除项；另写 AI 当前方案、必要的接续和模块入口。不知道的写"待核实"，不当成确认。
- **模块**：有实际内容时，在 `docs/modules/模块名/` 建 `DESIGN.md`；需要持续维护实现时，同目录建 `IMPLEMENTATION.md`。

没有 Node 时手动接入：复制 `AGENTS.md`、`docs/ADOPTION.md`、`docs/standards/` 下的三份规范和 `docs/modules/README.md`；照 `tools/templates/` 里的模板写游戏的 README、PROJECT 和 `.gitignore`，不复制框架自己的状态。`LICENSE` 存为 `docs/release/FRAMEWORK-LICENSE.txt`，不覆盖游戏的许可，也不推定游戏资产采用 MIT。本地材料默认放 `docs/local/` 并加入忽略规则，其他目录按需建立。

## 已有项目与升级

1. 读目标项目的规则和设计，对照已接入的版本和框架的 VERSION、CHANGELOG；保护现有的和未提交的工作。
2. 按差异合并到已有正文，分工只按[文档组织](standards/README.md#按模块组织项目文档)。
3. AGENTS 里的目录、状态、命令和案例挪到所属正文，AGENTS 保留阅读路由和权限底线；优先完善已有的导航。
4. 设计保留用户的要求和确认范围；实现和调试归同模块的实现文档；接续只留当前状态；历史过程保持当时的身份。
5. 旧计划、验收附件和重复副本按[验收规范](standards/acceptance.md)和已有授权收敛：核对内容和引用方之后才删重复项，保留唯一的成果、许可和必要的回退。不补造快照，不重跑历史验收，不迁移成固定格式。
6. 只处理授权范围内的事：不顺带合入功能、改写历史，也不撤销项目自己的约定。

从 0.1.x 升级到 0.2.0 时：

- "System"统一改叫"模块设计"，模块模板从 `docs/systems/README.md` 改到 `docs/modules/README.md`。
- 验收规范的留存改成两类：用户的材料，以及当轮计划定下要留的；其余都是临时产物，收尾时列清单删。原来"重要版本通常留 3–5 张截图"的说法取消，留多少由当轮计划写明。
- `tools/check.mjs` 增加了标题锚点检查；有英文 README 时，还检查中英文 README 的标题结构是否一致。

## 专项规范接入

优先合并项目已有的等效规范：AGENTS 保留触发条件和底线，README 维护目录，模块设计不重复规范正文。只同步某一份规范不等于完整升级；沿用项目的命令、本地位置和上传范围，不重建旧证据。没有相关改动时不用加载对应的规范，也不新增空规范、Skill、hook 或流程。

## 完成检查

- 现有入口能找到设计和实现，AGENTS 的路由能照着做，不要求每轮重读全部资料。
- PROJECT 和模块设计分清目标、已确认设计、AI 当前方案和未知项，没有扩大确认。
- 有效内容和必要的历史结论还在，删掉的东西如实标明能否取回，没有这次引入的重复正文或坏链。
- 在已有的接入信息里记下框架版本、来源 commit、完成和未核实的部分；还没有游戏工程时写明。
- 文档接入和宿主加载分开报告。宿主是否自动加载 AGENTS 要实测，例如开一个新上下文的任务，看它实际读了什么，不以 AI 的自述为唯一依据；没实测就写"未验证"。宿主不自动加载时，显式要求读取，或从宿主的规则入口引用，不猜造配置。

检查命令：`node <框架目录>/tools/check.mjs <目标目录>`，检查当前 Markdown 的本地链接和标题锚点；默认跳过本地资料和旧的历史过程目录，`plans/README.md` 仍然检查。要连历史一起查时加 `--local-evidence`，它不是默认的交付门槛。按改动核查锚点、生成入口和内容保留，分清遗留问题和本次引入的问题；工具不可用时做等价的检查。
