# 接入与升级

接入的目标是让 AI 找到清晰的用户要求和当前设计，保留有效内容与用户授权边界。只接入时不自动制作游戏、提交或推送。

## 新项目

目标不存在或为空时，用 `node <框架目录>/tools/adopt.mjs --target <目标目录>` 预览，再加 `--apply` 初始化。工具不安装引擎、不创建游戏工程或 Git 仓库。

生成后填写：
- PROJECT：用户确认的目标玩家、体验、核心循环、要求和排除项；另列 AI 当前整体方案、必要接续信息与系统入口。没有确认的内容不推定确认。
- System：有实际系统时再创建，仅包含已确认设计与 AI 当前设计方案，不写技术实现。

无 Node 时复制 AGENTS.md、docs/ADOPTION.md、docs/systems/README.md，并新建上述 PROJECT；不要复制框架自身的 PROJECT。将框架 LICENSE 保存为 docs/FRAMEWORK-LICENSE.txt，不覆盖游戏的 LICENSE，也不推定其代码或资产采用 MIT。Plan 和 references 按需使用，不预建。

## 已有项目与升级

1. 读取目标适用规则、设计与现有工作，保护未提交变更；升级比较采用版本与 CHANGELOG，不覆盖正文。
2. 新旧项目统一核心设计位置：项目方向与核心要求在 docs/PROJECT.md，系统设计在 docs/systems/。文件名可本地化，但须更新 AGENTS 直达路由。
3. 合并旧项目目标与状态时，PROJECT 只留影响接续的当前信息。System 中的技术实现、调试与开发过程转入已有工程说明或适当工作记录，保留有效知识；不因它们被 AI 记录就提升为确认设计。
4. 旧 Plan、验收报告与证据作为历史保留，不要求补齐或批量迁移到新的固定格式。它们不承担当前设计的权威来源；真正仍有效的用户要求应归入 PROJECT 或 System。
5. 核对转移内容再移除重复设计正文，同步文档、脚本与生成入口中的引用。保留原始证据及历史身份，外部大型材料沿用项目存储政策；不重跑全部历史验收。
6. 只处理本轮授权的目录或分支，不顺带合入功能或改写历史。保留目标项目独立约定的流程与权限；框架不强制 Plan、分支策略、默认 commit 或报告模板，也不借升级撤销用户另行明确的约定。

## 完成检查

- 分开报告“文档已接入”与“宿主加载已验证”。链接存在或提示用户读取不等于验证自动加载；未实测时写加载未验证，并给出显式读取提示。可通过一次新上下文任务观察是否实际读取相关依据和遵循规则，不以 AI 自述作为唯一证据。
- PROJECT 与 System 能回答目标是什么、哪些已确认、哪些由 AI 自主调整；未知项列明，确认范围没有被扩大。
- 有效设计、技术资料、历史结论和证据保留，没有重复的当前设计正文或本次引入的坏链。
- PROJECT 的简短接入信息记录框架版本、来源 commit、已完成与未核实部分；目标尚无工程时说明，不把文档接入完成当作游戏可运行。

用 `node <框架目录>/tools/check.mjs <目标目录>` 检查本地 Markdown 目标，并按改动核查锚点、生成入口和内容保留。遗留问题与本次问题区分。工具不可用时可等价检查，方法由实际任务决定。
