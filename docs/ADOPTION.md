# 接入与升级

## 新项目

1. 读取框架 AGENTS.md。用户只要求接入时不开始制作游戏。
2. 可用 `node <框架目录>/tools/adopt.mjs --target <目标目录>` 预览；确认目标不存在或为空，再加 `--apply` 写入。命令不要求使用 Bash，PowerShell 同样可用。只复制清单中的文档和空计划目录，不复制框架 .git、维护工具或虚构示例。
3. 无 Node 时手动复制 AGENTS.md、docs/README.md、PROJECT.md、STATUS.md、systems/README.md、plans/README.md、acceptance/README.md、acceptance/STANDARD.md、references/README.md、ADOPTION.md。按需创建计划目录。不要复制框架仓库的真实 STATUS 内容，改用下方接入记录。将框架 LICENSE 保存为 docs/FRAMEWORK-LICENSE.txt，保留框架的版权声明；不要覆盖项目自己的 LICENSE，也不推定游戏代码或资产采用 MIT。
4. 根据用户已提供的信息填写 PROJECT，未知项写“待确认”；不得将框架仓库定位写成目标游戏设计。
5. 核实并记录项目目录、引擎/运行时与版本、实际启动/检查命令、工具要求、权限与预算。没有代码的新项目可以注明“尚无工程入口”；这不阻止文档接入，但阻止声称可运行。
6. 更新 docs 导航、STATUS 和接入记录，按下方完成条件检查。若用户同时授权了开发任务，接入完成后直接继续；若只要求接入，则交付接入结果。无需额外等待一次启动确认。

## 已有项目

自动工具仅预览，不允许 --apply 写入非空目录。由 Agent 执行语义合并：

1. 读取目标根目录及适用的上层/模块规则，检查未提交变更、现有文档和当前运行入口。只读检查不要求项目必须干净。
2. 在 STATUS 或现有接续页记录“框架职责 → 实际文档路径”映射。例如 PROJECT → 现有白皮书，STATUS → 现有实现状态，systems → 现有模块说明。已有合理路径优先，不创建第二份同职能真相来源。
3. 在目标 AGENTS.md 合并适用的流程和设计边界，保留项目特有要求；将全部文档路由换成映射后的真实路径。内容有冲突，先核实用户最新要求和来源，只有无法判定的设计取舍才询问。
4. 仅补缺失的职责与骨架。现有历史验收先标明覆盖版本并加索引，不为接入批量拆分、移动、伪造版本或重跑所有历史测试。
5. 将框架 LICENSE 保留为 docs/FRAMEWORK-LICENSE.txt 或项目既有第三方许可位置，不覆盖项目自身 LICENSE。核实必要文档链接和项目工程入口。若只改文档，运行相关文档检查即可；接入操作本身不构成新一轮游戏功能验收。

## 接入记录与完成条件

在目标 STATUS 中维护简短接入记录（自动工具会预填版本）：

- 框架版本：版本号及可用的来源 commit；本地未发布版本明确标注。
- 文档映射：项目目标、状态、系统、计划、验收规范、验收索引的实际入口。
- 工程入口：目录、引擎/运行时、启动与验证命令；每项注明已核实或未配置。
- 特殊规则：用户批准的发布/付费边界、独立审核要求及预算（未约定不推定）。
- 接入结论：文档接入完成/仍有缺口，未配置项和下一步。

接入完成要求：适用规则没有已知冲突；关键路由有效；设计状态未被擅自提升；现有内容保留；未知项显式列明。代码未创建、引擎未选择的新项目可标“文档接入完成，工程尚未初始化”。已有项目工程入口未核实时，不声称可开始实际运行验证。

## 升级与回退

读取新版本 CHANGELOG，比较已采用版本与新规范。按职责逐项合并，仅更新适用规则；不得运行初始化命令覆盖已有项目。保留设计、工程约束和历史证据，检查链接后更新采用版本与重要差异。

使用项目既有版本管理保存可回退差异；是否提交/推送遵守用户授权。无版本控制时，必要备份保存在项目约定位置，不混入游戏资源。不要整仓覆盖回退而丢失用户后续工作。
