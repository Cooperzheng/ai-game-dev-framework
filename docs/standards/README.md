# 专项规范的组织与维护

一条规则只在一处写正文，其他地方链接过去。先合并已有的等效内容，不预建空规范、Skill 或庞大的目录；某个项目里的案例不自动变成所有项目的要求。

## 文档与 Skill 分工

- AGENTS：权限边界、核心底线和什么时候读什么。
- 专项规范（本目录）：适用条件和能观察的质量标准。
- 设计和技术事实：写在所属的正文里。
- Skill（可选）：可复用的知识、流程、脚本和模板。它引用同一份规范，不另立一套强制规则，也不代替 AGENTS 的阅读路由。

## 阅读路由

路由写清三件事：什么时候读、读哪份正文、底线是什么。规范可以跨目录适用。宿主是否支持局部规则、是否自动加载，要实际核实，见[接入指南](../ADOPTION.md#完成检查)。

## 按模块组织项目文档

从同一个模块目录找到设计和实现。每份正文只写一个模块或一种公共职责。

| 位置 | 写什么 |
| --- | --- |
| 根目录 README | 人和 AI 共用的完整导航，模块的设计和实现成对列出 |
| docs/PROJECT.md | 项目方向、核心要求和确认范围 |
| docs/modules/模块名/DESIGN.md | 玩家体验、规则、操作；已确认设计和 AI 当前方案（[模板](../modules/README.md)） |
| 同目录 IMPLEMENTATION.md | 实现、参数、制作方法、专用操作、有效的复验和未决问题；需要持续维护实现时才建 |
| docs/engineering/ | 跨模块的架构、全仓的运行维护和资产管线 |
| docs/standards/ | 质量标准和工作规范 |
| docs/references/ | 研究参考、来源，以及按项目政策保留的附件 |
| docs/release/ | 玩家说明、发行许可等交付输入 |
| docs/local/ | 本地的验收记录、可选计划、历史展示和配图，默认不上传 |

- **文件名可以本地化**：中文项目可以用"模块/模块名/设计.md、实现.md"，以及"工程""规范""参考""发行""本地资料"。已有的等效结构沿用，同名模块用同一个入口。
- **有内容才建文件**：小功能先写成已有文档的一节；只有设计的模块不补空的实现文档。
- **专用的放模块里**：模块专用的命令、复验和问题写在该模块的实现文档；全仓维护只留通用操作、必要的共用工作区台账、集成状态和链接。
- **只写现状**：有效结论替换过期的状态，不按时间堆流水；需要保留的历史注明版本和限制。设计里还没实现的要求保留。素材的 SOURCE、manifest 和许可证跟着资产维护。

迁移和改名时，先核对新旧路径、原文和依赖，再移动；然后修好链接、锚点、脚本、生成入口、忽略规则和资源跟踪规则。历史材料保持当时的身份，只更新有效的索引；缺失的证据不能改判为通过。历史检查的范围见[验收规范](acceptance.md)，不因缺少本地档案阻挡干净的检出。

## 可选工作记录

Plan 完全可选，结构自定，不按任务类型、规模或对话轮次强制创建。已有 Goal 直接作本轮工作记录，不再补一份 Plan；不强制阶段、模板、报告或证据目录，存放沿用项目政策，临时上下文不落盘。

Goal 写本轮目标、范围、具体验收、停止条件和结果；固定的测试、提交、留存规则引用项目规范，只写本轮差异。当前设计引用 PROJECT 或模块设计；有效结论和未决事项写回所属正文，历史记录保留当时范围。

## 维护

- 每条规则写清：什么时候 → 做什么，需要时给一个例子；写明适用范围和例外。
- 客观要求可以交给可靠的脚本检查；审美、信息价值和体验仍然要实际看。
- 用户的新要求更新到对应正文，同时清掉重复、冲突和过期的内容。
