# 专项规范的组织与维护

专项规范保存跨功能适用的质量要求。AGENTS 保留少量底线、适用条件与直达路由；README 或已有总览维护文档目录。修改前按任务读取相关规范，不要求每轮加载全部文档。

## 文档与 Skill 分工

| 内容 | 位置 |
|---|---|
| 必须遵守的工作边界、阅读触发条件 | AGENTS.md |
| 专项质量标准、判断依据与正反例 | 本目录或项目已有等效规范 |
| 游戏方向、功能与具体交互设计 | PROJECT / System |
| 技术接口、依赖与工程限制 | 项目技术文档 |
| 可复用的任务知识、执行流程、脚本与模板 | 按需建立的项目 Skill |

Skill 可以包含知识和流程，但不会自动获得更强约束力。强制规范通过 AGENTS 明确要求读取；Skill 引用同一正文，不建立第二套规则。不为每条反馈创建一个 Skill，也不要求每个项目安装 Skill。

## 阅读路由

路由写明“何时触发、读哪个文件、保留什么底线、怎样验证”。例如：修改玩家可见界面、文案、布局或交互前，读取 UI 规范和相关 System；交付前按规范检查实际画面与操作。

规范可以跨代码目录适用，不能只根据文件夹名称判断任务范围。目录专属技术约束可使用宿主支持的局部规则，但须核实加载方式。链接存在不代表正文已加载；不支持自动加载时显式读取。

## 按模块组织项目文档

从项目目录直接找到模块，再在模块内区分设计与实现。默认采用下列职责；文件名可以本地化，已有等效结构按授权范围迁移，不预建空目录或空正文。

| 位置 | 单一职责 |
| --- | --- |
| 根 README | 人和 AI 共用的完整导航；模块设计与实现成对列出，只链接已有文件 |
| docs/PROJECT.md | 项目方向、核心要求和设计确认范围 |
| docs/modules/模块名/DESIGN.md | 该模块的玩家体验、规则、操作、已确认设计与 AI 当前方案 |
| 同目录 IMPLEMENTATION.md | 该模块的实现、参数、制作、专用操作、有效复验和未决问题；有维护需要时才建立 |
| docs/engineering/ | 跨模块架构、全仓运行维护、资产管线；每份只承担一种公共职责 |
| docs/standards/ | 质量标准与工作规范 |
| docs/references/ | 研究参考、来源说明和按项目政策保留的参考附件 |
| docs/release/ | 玩家说明、发行所需许可等交付输入 |
| docs/local/ | 本地验收、可选计划、历史展示及配图；默认不上传，不作为当前设计正文 |

中文项目可对应为“模块/模块名/设计.md、实现.md”“工程”“规范”“参考”“发行”“本地资料”。同一模块的设计和实现使用同一个模块名称，不再将设计放 systems、实现散放 docs 根目录；仅有设计的模块不补空实现文件。

模块按可持续维护的责任划分，模块内部的小功能优先作为章节；不要为一个按钮、一次反馈或每轮验收新增文档。设计中的未实现要求保留，工程正文不能替用户补做确认。素材目录的 SOURCE、manifest 和许可证继续随资产维护，不合并到设计正文。

完整目录只维护在 README；AGENTS 保留读取条件，其余总览只在必要上下文中引用。模块专用命令、复验与问题留在该模块实现；全仓维护仅记录通用命令、必要共用工作区台账和整仓集成状态。有效结论替换过期状态，必要历史注明版本与限制，不堆叠每轮流水。

迁移先列明旧新路径、原文与依赖，再移动并核对内容，修复 Markdown/HTML 链接、标题锚点、脚本、生成模板、忽略规则及资源跟踪规则。历史材料保持原阶段身份；仍在使用的索引和入口更新，已缺失的证据不能改判通过。检查器覆盖当前共享正文，本地档案按需检查，缺少本地档案不阻挡干净检出。

## 可选工作记录

Plan 只在跨会话接续、路线比较或工作安排有价值时采用，沿用项目本地存储政策，不强制阶段、模板或报告。临时上下文不落盘；确需记录时注明日期、范围、进度和未决取舍，完成后将有效知识更新所属正文。旧计划不产生新的实施授权，也不覆盖当前设计。

## 维护边界

- 一条规则只保留一份详细正文，其余入口引用；已有等效规范优先合并，文件名可本地化并同步路由。
- 按稳定主题归类，只在真实需求出现时增加规范，不预建空文档或庞大目录体系。
- 写明适用范围、例外和可观察的合格标准，避免“严格遵循最佳实践”等不可操作要求。
- 用户新要求回写相应正文，清理重复、冲突和过期规则；案例不自动升级为所有项目的强制设计。
- 能可靠自动验证的要求可落入检查脚本；审美、信息价值和体验仍需实际审核，不以文字声明或文件存在代替。
