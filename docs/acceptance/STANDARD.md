# 验收与归档规范

## 建档时机

大功能交付、该类工作的阶段收束，或用户明确要求的专项验收建立独立档案。小修、参数试验和中途检查归入所属工作，不各建档；复杂内部工作不因建立 Plan 或阶段收束就必须创建大功能验收档案，按范围保存必要结果与交接。大功能未达标后收束也如实归档。

## 目录与版本

目录使用 `YYYY-MM-DD_功能简介/`，同日同名需要区分时增加 HHmm；目录日期为交付日期，报告另记测试时间与时区。

每个目录包含 REPORT.md；较长独立审核使用 REVIEW.md；关键证据放 evidence/。不要为没有审核或证据的内容创建空报告。

报告记录受测 commit、实际运行入口和效果配置，关键资产按需记录版本或哈希。未提交的改动应保存基准 commit 与受测改动快照；不能把基准 commit 冒充受测全部状态。历史版本缺失明确标注，不补造。

## 主报告内容

- 本次交付、体验目标和范围，以及对应版本的 Plan/设计依据。
- 受测版本、测试时间、设备与环境、运行入口和关键配置。
- 原目标逐项兑现程度；适用的功能、画面、动态、性能检查及必要回归。
- 通过、未通过、未检查内容，独立审核覆盖范围和用户反馈。
- 关键证据与复验入口、遗留问题、后续处理和是否采用默认配置。

运行正确、局部改善和整体达标分别判断。技术测试通过不代表玩法或画面设计获用户确认。只检查静图不得宣称连续操作或性能通过。

## 证据保存与复验

关键原图、小型结果文件和必要复验脚本应持久保存，不仅引用被忽略的临时目录。大录像按项目存储政策归档，并记录固定位置和校验信息。参考图与实机图清楚区分。

同次交付的补充复验在原目录下按时间与受测版本留痕，不覆盖旧证据；形成新一轮大功能交付再建目录。旧结论错误时记录更正原因和替代结果，保留原始追溯。

交付后更新本目录索引、对应系统落实情况和当前状态，并归档阶段计划。关键证据缺失时明确限制，不通过重新描述补成已验证。

## 可复制的 REPORT.md 骨架

```markdown
# 交付功能简介

- 交付日期 / 测试时间与时区：
- 结论：通过指定范围 / 部分通过 / 未达标 / 证据不足
- 受测版本：commit；未提交改动快照；关键资产身份
- 设计与计划依据：当时版本或随档快照
- 实际入口 / 配置 / 设备环境：

## 目标兑现
| 原始目标 | 结果与证据 | 未覆盖或未通过部分 |
| --- | --- | --- |

## 检查与审核
实际操作路径、适用的功能/画面/动态/性能检查及必要回归。
独立审核的参与者角色、实际查看范围；未开展则明确说明。

## 证据清单
| 文件或持久链接 | 对应版本与采集条件 | 支持的结论 |
| --- | --- | --- |

## 遗留问题与采用结论
哪些进入默认版本，哪些保留候选，哪些需要后续工作。
用户设计确认状态与技术结果分别说明。

## 同步与复验
系统、状态、索引和归档计划的链接；补充复验的时间、版本与结论。
```

同一目录可以用 `rechecks/YYYY-MM-DD_HHmm.md` 保存补充复验，配套证据用不同子目录或唯一文件名。主报告保留原结论并链接复验，不用新版本结论替换旧事实。

## 本地交付提交

大功能验收收束 → 同步 System、STATUS、索引与 Plan → 检查差异和暂存区 → 本地 commit。小修不强制逐次单独提交，专项检查是否提交按实际交付范围和授权判断。

- 只纳入本次相关代码、资源、文档与验收证据；不直接用全量暂存混入其他任务。不撤销用户已有暂存内容；无法安全隔离时保留现场并说明需要解决的具体归属问题。
- 通过、部分通过或未达标收束都可提交；commit 是可追溯节点，不是品质通过证明。敏感信息、临时数据和不应入库的大文件按项目规则处理，外部证据保留固定引用。
- 报告记录受测 commit 或基准 commit 加受测快照；最终交付 commit 可另外包含验收报告与文档同步。验收后改动运行代码或资源，须补做受影响检查再提交，不能把旧结果算给新代码。
- 最终 commit 哈希在交付回复中提供，无需写回该 commit 自己包含的报告。无需为填自引用哈希反复 amend 或创建额外提交。
- 没有 Git 仓库、提交身份未配置、钩子失败或无实际差异时，说明实际情况；不擅自初始化仓库、猜测身份、跳过钩子或创建空提交。可在授权内修复本次问题后重试。
- 本地 commit 不自动授权 push、发布、force push 或历史改写。用户明确要求不提交时，保留结果并注明未提交。

## 分支合并与验证

分支约定和同步时机以 [AGENTS.md](../../AGENTS.md#开工前的分支约定) 为准。直接在主干工作也遵守相同的文档与受测版本要求。

- 合并前检查相关代码、资源、系统文档、STATUS、Plan 和适用验收记录是否完整，未实现、未接入、未验证项保持明确；不适用或无变化的文档无需重写。
- 代码与文档随同一轮合并进入目标分支。解决冲突时核对双方的最终行为、设计依据与接续状态，不能只以 Git 没有冲突判断文档正确，也不能直接用一侧文档覆盖另一侧有效变化。
- 合并后记录实际整合版本，执行项目要求的检查；目标分支变化、冲突解决或入口/配置/资源变化影响行为时，补做相关验证。原受测内容未变化时可引用已有证据并说明适用依据，不为合并机械重跑全部历史验收；未检查范围如实保留。
- 历史报告保留原受测版本和结论；补充验证按前述复验规则追加，不把旧报告改成新版本已通过。合并后尚未完成必要验证时不得宣称正式版本已验收；交付回复区分已提交、已合并、已推送和已发布。
