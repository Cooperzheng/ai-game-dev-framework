# AI Game Dev Framework · AI 游戏开发框架

简体中文 | [English](README.en.md)

**让 AI 在持续开发中，始终能清晰找到核心目标、用户需求和当前游戏设计，提高一致性。**

框架为 AI 提供稳定的设计依据。如何拆任务、选技术、实现和验证，由 AI 结合实际情况决定；Plan 完全可选，不要求固定工作流程、验收档案或默认提交。适用于新游戏和已有项目，不绑定引擎、模型或插件。

## 体验要求决定是否完成

用户要求的玩法、画面、操作感受及明确认可的参考效果，是完成判断的依据。

例如用户想要参考图中的厚重云层：接入体积云、成功运行或测试通过，都不能单独证明目标已达成。AI 需要在可比条件下对照参考，检查云层形态、明暗层次和质感；不足时继续调整，遇到限制就说明差距与取舍，不自行降低目标后宣布完成。

参考只采用用户明确认可的部分。用户只认可云的质感，就不能把图中的地形、色调与整套风格也算作授权。[完整虚构示例](docs/references/WORKED-EXAMPLE.md)。

README 的文档入口供人和 AI 共用；已有等效总览时沿用，不另建 AI 专用目录。AGENTS 保留“什么时候必须读什么”，具体目录和项目状态不在其中重复维护。详细命令、模板与工程案例放入按需读取的文档，保留适用条件和有效约束。技术架构管理接口与工程限制，不覆盖设计授权。

设计者主要阅读 PROJECT 与 System 中的“已确认设计”，也可以查看 AI 当前方案。AI 维护必要接续信息；技术实现不混入设计正文。

### 区分确认设计与 AI 当前方案

- **已确认设计：**你明确要求的目标、规则和排除项，注明来源与认可范围；改变含义前需要与你对齐。
- **AI 当前方案：**当前采用的设计细节，可在已确认边界和任务范围内自主调整，重要体验变化说明原因与结果。

已经实现、技术测试通过、局部认可或没有提出反对，都不等于整体设计确认。已确认但尚未实现的要求保留，明确说明差距。

例如你确认“主动躲避，不引入体力管理”，AI 当前方案可采用闪避和翻滚，并自主调校未经你明确确认的冷却；不能自行加入体力消耗。

## 专项规范与 Skill

AGENTS 保存少量底线和明确的阅读触发条件，专项质量要求在[规范文档](docs/standards/README.md)单处维护。[UI 基础规范](docs/standards/ui.md)覆盖文案用途、信息层级与实际操作验收；具体游戏设计仍由 PROJECT/System 决定。Skill 可按需封装知识与重复流程并引用规范，不作为强制规则唯一入口。按真实需求增加主题，不预建空规范。

## 怎样使用

缺少背景或涉及整体方向时读 PROJECT；改设计或玩家可感知行为前，从系统入口读取相关 System，入口缺失则搜索现有资料。仅复用已读且仍有效或对话已完整提供的依据。新要求与当前玩法变化在交付前回到设计正文；纯技术改动无需改设计，用户要求不落盘时遵从。交付回应原体验要求，说明实际观察依据与剩余差距。

Plan 由 AI 按需要选择使用，工程经验留在代码注释、已有工程说明或可选工作记录中。历史过程可以保留，但不能覆盖当前设计依据。不预建空系统、任务目录、报告或索引。

宿主不自动加载 AGENTS 时，显式要求读取，或从宿主支持的规则入口引用它。文档接入与宿主加载须分别报告；未实测时注明加载未验证，链接与初始化测试不证明 AI 行为符合预期。框架无法保证每个 Agent 都自动遵循规则。

交付收尾从已有文档入口核对设计、运行说明和验收范围；区分本次通过、失败、未执行、历史和过期结果。作为依据的验证须识别受测文件及环境，未提交工作区不能只写HEAD；重跑保留原件，相关输入变化后补做受影响检查。交付可玩入口前实际确认启动与主入口操作，数据位置变化说明存档影响。详见[收尾规则](AGENTS.md#交付收尾与证据一致性)。

自动检查或hook由项目按需采用：优先可靠脚本，再考虑提醒或有限阻断，不强制安装、不将工具异常算通过，也不使普通讨论、诚实失败报告或用户中断无限续跑。初始化工具仍只生成核心文档，不附带宿主hook。

## 让 AI 接入项目

在目标游戏项目中发送：

> 请将 https://github.com/Cooperzheng/ai-game-dev-framework 接入当前项目。先读 BOOTSTRAP.md。以体验目标与设计一致性为核心，将项目方向与用户要求归入 PROJECT，系统纯设计归入 systems，区分已确认设计与 AI 当前方案。保留有效内容、工程知识和历史记录，同步引用，不引入强制 Plan 或开发流程。完成检查并报告实际入口和缺口。本次只接入，不提交或推送。

[接入指南](docs/ADOPTION.md) 说明新旧项目及升级处理。已有项目统一核心设计目录，按职责合并；已有用户明确约定继续保留，旧 Plan 与验收结果不批量重写。框架自身的 [PROJECT](docs/PROJECT.md) 只描述框架，不能复制成目标游戏状态。

## 可选初始化工具

需要 Git 获取仓库；初始化工具要求 Node.js 18+，无第三方依赖。

```sh
git clone https://github.com/Cooperzheng/ai-game-dev-framework.git
node ai-game-dev-framework/tools/adopt.mjs --target ../my-game
node ai-game-dev-framework/tools/adopt.mjs --target ../my-game --apply
```

第一条 node 命令只预览；--apply 只接受不存在或为空的目标，非空目录（包括只有 .git）由 Agent 按指南合并。路径相对终端当前目录，含空格时加引号；框架副本与游戏目录分开。

默认生成简短 README 文档入口、核心文档、系统填写说明、专项规范说明与 UI 基础规范、接入指南与框架许可；不生成 Plan、验收目录或参考库。工具不安装引擎、创建游戏代码、初始化 Git 或提交。填写真实设计依据后才算接入完成；无 Node 可手动接入。

## 维护与验证

版本见 [VERSION](VERSION)，变化与本轮检查见 [CHANGELOG](CHANGELOG.md)。升级比较合并，不自动覆盖下游或丢失确认要求。

框架维护检查：`node tools/check.mjs`、`node --test tools/adopt.test.mjs`、Git 差异检查。它们验证文档引用与初始化行为，不证明真实游戏体验、全周期一致性或已有项目迁移已通过。
